## 1. What I found (file:line, quoted — line numbers at this head)

**The lock.** The Force surface's recording-context lock is fed, among five inputs, by the
guided session object itself:

- `Sources/Features/Force/ForceView.swift:1639` —
  `private var guidedSessionIsActive: Bool { guidedSession != nil }`
- `:1643` — `private var guidedControlsLocked: Bool { guidedSessionIsActive || guidedLaunch.inFlight }`
- `:1853` — `private var recordingContextLocked: Bool { ForceContextLockPolicy.isLocked(
  ForceContextLockState(… guidedSessionActive: guidedControlsLocked )) }`

So the lock's guided input is **the presence of the in-memory `@State` session object**, not
"a session that can still do something". `GuidedForceProtocolSession` is a live `@MainActor`
state object (`ForceView.swift:18`) with `isEnded` and `teardown()` (`:542`).

**Every affordance that could clear it is conditioned on `!isEnded`.**

- Resume/End card: `:1890` — `if let guidedSession, !guidedSession.isEnded { GuidedForceResumeCard(…) }`
  — an ended session hides the only Resume/End pair.
- The guided cover itself: the minimize path sets `guidedMinimizeRequested = true` and
  dismisses (`:2156-2157`); the cover's own onClose calls `clearGuidedSession` — for an
  ended session dismissed/minimized earlier, neither is reachable any more.
- Re-entry does not restore it: the cover's re-presentation path re-registers teardown but
  renders the resume card only for a non-ended session (same `:1890`).
- The device row said `"Guided protocol active — resume or end it above"` unconditionally
  (now `ForceLockOrphanPolicy.activeLockLabel`, `ForceView.swift:3063`) — i.e. it claimed a
  resume/end affordance that did not exist.

**How an ended session ends up holding the surface (reachable, not hypothetical).**
The session ticker runs independent of the cover's presentation
(`ForceView.swift:292` — `if case .interrupted = model.tindeq.status { await preserveInterruption(at: date) }`).
`preserveInterruption` (`:446`) claims the terminal settlement on a mid-pull interruption.
If the protocol was minimized first and then the pull is interrupted (disconnect, strap
loss), the session reaches its terminal, ended state **while its cover is not presented** —
and from that moment every clear path in the UI is gone while `guidedSession != nil` keeps
`guidedControlsLocked` true. The result is the reported shape: the surface locked, with
nothing left to resume or end. This lane found no persisted or external owner (below), so
the lock was in-process only — its owner is exactly `guidedSession`.

## 2. Candidate verdicts (§2 of the brief)

Executed probes are committed as `candidate-01…04*.log.gz` (raw exits inside).

1. **Orphaned Live Activity (`GuidedProtocolActivityManager`) — ELIMINATED.**
   The guided Live Activity carries no interactive element that can start/resume a session
   (`GuidedProtocolLiveActivity.swift`: no Button/Intent — only `.widgetURL("sendmeter://force")`,
   a deep link to the tab), and the launch orphan sweep only **ends** lingering cards
   (`AppModel.swift:1815-1816` → `GuidedProtocolActivityManager.reconcileOrphans()`, guarded on
   `!isActive`). Nothing in the manager writes any of the lock's five inputs.
2. **Watch / WatchConnectivity ownership — ELIMINATED.**
   The watch's `liveForce` is display-only: one consumer in the Force view (the remote-mirror
   card, `ForceView.swift:2037`); the lock's inputs never read it. The phone's watch message
   kinds (`WatchConnectivityService.swift:251-263`: `requestSession`, `liveWorkout`,
   `liveForce`, `workoutCompleted`, `queueStatus`) never write guided session state;
   `requestSession` is the access-token relay (`onSessionRequested`, `AppModel.swift:969`),
   not a Force session.
3. **A persisted in-flight session / durable intent restored at launch — ELIMINATED.**
   `GuidedForceProtocolSession` has exactly two constructors (the live launch at
   `ForceView.swift:2724` and the DEBUG fixture at `:4094`); `GuidedLaunchLifecycle` is in-memory
   `@State`; the durable queue's payload kinds (`PendingWrite`) contain no guided-session
   kind; no restore path reconstructs a session. A relaunch therefore cannot hold this lock,
   and cannot re-create the orphan.
4. **Session-ownership / lease state in the cache — ELIMINATED.**
   The cache schema has no lease/ownership/owner table (`LocalCacheStore` tables:
   `cache_rows`, `sync_cursors`, `sync_boundaries`, `cache_quarantine`), and the lock reads
   in-memory state only (predicate verbatim in `candidate-04` log). Nothing cache-side can
   hold the Force surface.

Net: the only owner that can hold the lock with no affordance is the **in-memory ended
session** — attributed by read state, not by a persisted identifier, because that is all the
boundary has.

## 3. Deliverable

### 3.1 The release (implemented at the boundary that owns the lock)

- **New Core policy** `Sources/Core/ForceLockRecovery.swift` (88 lines):
  `ForceGuidedLockReadState { sessionPresent, sessionEnded, launchInFlight }` (`:41`),
  `ForceGuidedLockOwner { none, resumableSession, launchInFlight, endedSession }` (`:19-30`),
  `ForceLockOrphanPolicy.owner(_:)` (`:62`) and `.requiresRelease(_:)` (`:72`).
  Decision table: no session and no launch → `none`; live session → `resumableSession`;
  no session but launch in flight → `launchInFlight` (#1005's failure-card case); **ended
  session → `endedSession` (the orphan) → release required**. The policy also owns all copy:
  `releaseTitle` = "Clear Finished Session" (`:78`), heading/notice/hint (`:79-81`), plus the
  two device-row labels (`:83`, `:87`).
- **Force surface** `ForceView.swift`: `guidedLockOwner` (`:1650`) and `guidedLockOrphaned`
  (`:1663`) computed through that policy; the release card renders exactly on the orphan
  (`:1916` — `if guidedLockOrphaned { GuidedSessionReleaseCard { releaseFinishedGuidedSession() } }`);
  `GuidedSessionReleaseCard` (`:2795`, internal so the render test can capture the real
  component) shows the heading, the notice, and one **Clear Finished Session** button
  (accessibility id `guided-session-release`); the device row now names the orphaned state
  (`:3063`) instead of claiming a resume that does not exist.
- **One implementation**: `releaseFinishedGuidedSession()` (`:2267`) refuses a live session,
  joins the already-settled terminal flight (`await session.teardown()`), then clears the
  view state. The lifecycle teardown's ended branch (`:2276` region) runs the **same**
  function, so no second path can drift.

Why this is safe by construction: for an ended session `teardown()` takes its early return
(terminalSettlement already claimed → `await terminalSettlement.wait(); return`,
`ForceView.swift:543-546`). The release therefore performs **no salvage, no write, no
clear** — it only waits for a flight that has already settled and then drops the view state.

### 3.2 Data-safety fence — what happens to un-synced data on that path

**Nothing.** Stated plainly, for each surface:

- **Durable queue (`pending-writes.json`):** untouched. The release reaches no queue API —
  enforced statically by the wiring test (below) and measured behaviourally by the app test,
  which reads the queue file in the same main-actor turn immediately before and after the
  release's join and requires the id set before to remain a subset of the id set after.
- **Un-synced recording:** stays queued and stays published to the app (same test).
- **Device-held pull** (`completedSummary` / `interruptedRecording`): untouched; the release
  clears no device summary, so a pull still recoverable via the #1005 recovery card remains
  recoverable.
- **Cursor/ordering:** no call of any kind to the queue's ordering/watermark machinery.

### 3.3 The owner's interim workaround (device-level, with evidence)

- **Force-quit and reopen — clears it.** Every input of the lock is in-process (@State) and
  the orphan is the in-memory session (candidate 3, eliminated restore paths): process death
  drops the session, so the lock cannot survive a relaunch. At the next launch the stranded
  Live Activity card is ended by `reconcileOrphans` (candidate 1). This is the interim
  guidance — and, per §8 of the brief, the **only** one: never uninstall/reinstall (that
  wipes the local cache and the durable queue and can destroy an unsynced recording).
- **Dismissing/ending the Live Activity alone — does NOT clear the in-app lock** (the card is
  display-only; nothing in the manager feeds the lock's inputs), though it is harmless.
- **Ending the session on the watch — does NOT clear it** (no watch input exists in the lock).
- **Rebooting the phone — clears it**, for the same reason as force-quit (process death).
  Note for anything device-held before the reboot: an unsaved pull is re-offered by its own
  recovery card after relaunch; nothing is silently thrown away by the reboot itself.

**What I could not determine:** which of these the owner actually experienced — there is no
device log from his unit (see §4), so I cannot confirm the stuck state was this orphan
rather than an earlier build's shape. If he is still stuck, ask him to try
**force-quit and reopen first**; if the surface is still locked with nothing to resume/end,
this lane's release is the fix to ship.
