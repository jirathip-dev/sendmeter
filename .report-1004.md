## 2. FIRST DELIVERABLE — which case is the owner in?

Established by enumerating the two disabled conditions from source and driving the reachable states, **not** by
staring at the view. Anchors are against `43c7cc5`.

**The two sides.**
- *Start disabled:* `device.hasUnsavedRecording` (`ForceView.swift:2986`, `:2993` `.disabled(device.hasUnsavedRecording)`;
  the same predicate locks the recording context through `ForceContextLockPolicy` at `:1828`/`:1834`), where
  `hasUnsavedRecording = completedSummary != nil || interruptedSummary != nil` (`TindeqBluetooth.swift:71`).
- *Save/Discard disabled (pre-fix):* `.disabled(savingSummary || guidedSessionActive)` on all four buttons
  (`ForceView.swift:2849`, `:2855`, `:2867`, `:2873` at base), where the passed-in `guidedSessionActive` is
  `guidedControlsLocked = guidedSessionIsActive || guidedLaunchInFlight` (`:1637`, `:1834`).

**Simultaneous-disable ⟺ `hasUnsavedRecording && guidedControlsLocked`.**

**(B) — the card IS rendered and BOTH buttons are greyed. REACHABLE, in-process, and this is the P0.**
The exact reachable sequence: a guided session is running → the Progressor disconnects mid-pull →
`didDisconnectPeripheral` sets `interruptedSummary` (`TindeqBluetooth.swift:477` → `hasUnsavedRecording == true`) →
the `.interrupted` handler deliberately **skips** the salvage while `forceModel.guidedProtocolActive`
(`AppModel.swift:1117`), so the summary stays held and the guided session stays alive → Start is disabled by the
held pull and Save/Discard are disabled by `guidedSessionActive`. If the holder is the *launch flag* instead of a
session (`guidedLaunchInFlight` with no session to end), there is **no in-process escape at all** — that is the
"Start greyed with no explanation" the owner reports, and at base the flag has no deadline, so it is cleared only by
the branches that happen to return (`:2507`, `:2515`, `:2529` at base).

**(C) — the card is TAPPABLE but the save path fails. The other live half (the owner confirms this banner is still
showing).** `save()` calls `model.saveForceSummary`; on `enqueued == false` the summary is deliberately left with the
device (the rep is reported through `LostRecordingStore`), so the pull stays held, Start stays disabled, and at base
the card gave the user no explicit offer of discard. The `.dataUnreadable` banner is the decode family
(`DecodingError` / `LocalCacheError.invalidPayload` / `DeltaReadError` — `FriendlyError.swift:145-160`, `:487-508`).

**(A) — the card is NOT rendered at all. NOT REACHABLE in the shipped code (enumerated).** A held pull is either
`interruptedRecording != nil` (first card variant, `:2842`) or `completedSummary != nil` (second variant, `:2860`,
gated only on `status != .measuring`). The only non-rendering shape would be `completedSummary != nil && status ==
.measuring`, and `stopMeasuring()` — the only writer of `completedSummary` — always assigns `status = .connected` or
`.idle` before returning (`TindeqBluetooth.swift:156-183`). So a held pull always has a rendered card; the owner's
symptom is a rendered-but-dead or failing card, not a missing one.

**(D) — what could NOT be established.** The owner's *persistence across many force-quit + relaunch cycles* cannot be
attributed from the evidence available on this host. Both lock owners are per-process state
(`guidedSession`/`guidedLaunchInFlight` are `@State` on the ForceView, `completedSummary`/`interruptedSummary` are
in-memory on `TindeqBluetooth`), so a relaunch does clear them; the two candidates that would reproduce a
repeat-lock are (i) the awaited target resolution not settling on every attempt (no deadline at base; the transport
supplies only its own URLSession timeout) and (ii) the save failing on every attempt. **Neither can be pinned without
the device log, which is unavailable (§3).** This lane therefore fixes both mechanically rather than guessing.

**A held-but-unrenderable pull:** does not exist in this build — see (A). What exists is a rendered card whose actions
are both unreachable, which is the defect, and which the recovery policy now makes impossible (test AC-4 below).

## 4. Acceptance criteria — disposition

**Issue half 1 — the app must never be left unable to start a session; the flag cannot outlive the attempt.**
`GuidedLaunchLifecycle` owns the flag: `begin(preset:)` returns an attempt id, `settle(_:outcome:)` is the single
release point, and a stale settlement is a no-op (it cannot clear a newer attempt's flag). Every launch exits through
`settle` — including the deadline, the superseded/account-change guard, a refusal and success. The resolution now
runs inside one bounded await (`ForceView.resolveGuidedLaunch`, 12 s) so a resolution that never settles can no
longer hold Start. A deadlined attempt shows a row that says **why** (the account's recorded load-failure class when
one exists, otherwise the timeout) with **Try Again**, which re-runs the same `launch(preset:)` with the preset the
failure carries.

**Issue half 2 — an undecodable stored payload must not dead-end the app.**
The coherent read stops skip-`try?`-ing: it reports `invalidRows`. On the launch path (and on demand from Settings)
each non-pending invalid row is copied verbatim into `cache_quarantine`, removed from `cache_rows`, and its entity's
cursor + boundary are deleted so the next refresh is a full authoritative reconcile (the heal). **What happens to
un-synced data, explicitly: nothing — a pending row is never copied, never deleted, never cursor-reset; it is
reported (notice + log) and left exactly where it is.** Quarantine rows are never auto-deleted, so a later build can
recover the raw bytes.

**Issue half 3 — name it from the log.** UNAVAILABLE; see §3. The new failure path is logged in the same persisted
form so the next capture carries it.

**Conductor AC (new) — the two disabled conditions must never be simultaneously satisfiable.**
`ForceRecoveryActionPolicy` decides the recovery controls from the held pull alone (`hasUnsavedRecording`, `saving`,
`saveFailed`); `sessionActive` is carried as an input **so a pin can prove it inert**. The card's four buttons now
read `!canSave` / `!canDiscard` from that policy, and a failed save (`enqueued == false`) sets the fallback that shows
the discard notice while Discard stays available. The exhaustive matrix test asserts the invariant over all 16
combinations, and a second test compares against the *pre-fix condition verbatim* (`saving || guidedSessionActive`)
to show the policy cannot reproduce the deadlock cell.

**"No weakening — the decode failure must stay visible in the log and in a non-blocking surface."**
The repair writes the persisted launch-failure line and publishes `lastLocalDataRepair`; Settings renders the notice
(`local-repair-notice`), which states both what was set aside/rebuild and that unsynced data was not touched. Nothing
silences the failure and nothing is auto-deleted.

**Data safety (hard rule).** No uninstall/reinstall remedy is advised, implemented or hinted anywhere in this diff or
its copy; the quarantine preserves the raw payload; the pending boundary is the data-safety rule in code
(`LocalCacheRepair.swift`), in tests (`testAPendingUndecodableRowIsPreservedInPlace`) and in the user copy.
