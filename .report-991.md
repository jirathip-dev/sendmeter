## What changed and why

The cold-launch console error

    Using kCFPreferencesAnyUser with a container is only allowed for System Containers, detaching from cfprefsd

came from the app's own App Group store use on the launch chain — not from
Apple's WatchConnectivity. `ReadinessWidgetStore.appGroupStore` was built with
`UserDefaults(suiteName: "group.com.jirathip.sendlog")`; a suite registers
AnyUser domains next to the CurrentUser ones (CFApplicationPreferences.c,
`_CFPreferencesStandardDomainSetSuite` — quoted in
`docs/evidence/issue-991/991-mechanism.txt`), and a containerized process may
not read an AnyUser source, so cfprefsd refuses it once per process on the
first suite use and the source detaches.

Fix: the store now reads and writes the App Group domain through an explicit
`kCFPreferencesCurrentUser` access (`ReadinessWidgetAppGroupDefaults`,
`CFPreferencesCopyValue` / `CFPreferencesSetValue` +
`CFPreferencesAppSynchronize`), behind a `ReadinessWidgetDefaults` protocol
that `UserDefaults` also conforms to for injected tests. Domain, key and plist
schema are unchanged; `appGroupStore` is now non-optional (the accessor always
exists; a missing container degrades to a nil read, as before).

Route chosen — **API, not sequencing**: `CFPreferences` with an explicit
CurrentUser is the API valid for an app-group container (the CurrentUser
source is the one the process's container is attached to). Sequencing after
container attachment is not needed: the transcript shows the container lookup
and sandbox-extension consumption already succeed on the same thread ~1 ms
*before* the refused AnyUser source exists (`.581`/`.583`/`.584` above), so
there was no ordering bug to fix — the bug was the suite API registering an
AnyUser source that cannot attach to any container. Removing the app-group
usage or swapping to per-process storage would have been forbidden road; the
shared container, its key and its schema are all preserved.

## Failure behaviour answer (throw? nil? quiet? banner?)

* `ReadinessWidgetStore.load()` is non-throwing and returns `nil` for
  "nothing stored" — and a refused containerized read also degrades to a nil
  (or empty) read, so the user-visible symptom of the bug is the widget
  showing nothing / "Waiting for today's score", never a banner.
* There is no thrown error on this path for a banner to catch; the only
  surface was the console line from cfprefsd itself.
* The one remaining silent degradation — `save()` that does not read back
  (unreachable container, protected plist) — now logs at `.notice`
  (persisted, #992) with subsystem `com.jirathip.sendlog`, category
  `readiness-widget`, so a device capture can name it.
* On the reset path a `clear()` of an absent key is a no-op write; the fix
  changes no data and can lose none.
* **Was any user state silently degraded before this fix?** No stored state
  was lost by this read. The suite's own write lands in the first
  (CurrentUser) suite domain — the one the container attaches to — which is
  exactly the domain the simulator probe read back (`step2 cf-read bytes=3
  equalSuite=true`); the refused source is the AnyUser twin, which never held
  the app's data (`Container: (null)` in the device line). The container
  lookup and sandbox extension succeed on the same thread 1 ms *before* the
  refusal (transcript lines above), so the containerized CurrentUser read
  path worked throughout; the defect was the refusal + `detaching from
  cfprefsd` for the AnyUser source, plus the latent failure mode (a read
  that cannot reach the container degrades to `nil` = "no data yet"). The
  app-group payload's user-visible state (widget glance data) was therefore
  not silently wrong — but a genuinely unreachable container would have been
  silent before this change, which is why the save-that-does-not-read-back
  notice was added.
