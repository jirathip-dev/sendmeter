## Root cause

Not a conditional, not a wrong hand-count: **two statements were multi-column
`select is(...), is(...), …`**. psql prints a multi-column result set as ONE
line, the TAP lines joined by ` | `:

```
 ok 18 - GREEN: the survivor keeps its own group id | ok 19 - GREEN: duration is the full span (10:00:00 → 11:01:00) | ok 20 … | ok 21 …
```

A TAP consumer reads only the FIRST test number per line, so test numbers
**19, 20, 21** (the GREEN statement's 2nd–4th columns) and **32** (the RETRY
statement's 2nd column) never entered the stream. The file emitted 33 tests
while `plan(37)` promised 37, so every number from 19 onward was shifted by 3 —
`Found (22) but expected (19)` — and pg_prove failed the file even though **no
assertion was wrong** (`Failed: 0`).

(Why my round-1 local scratch run missed it: the pgTAP-compatible shim counts
assertions internally and never parses stdout, so the garbled emission stayed
invisible; `grep -c '^ok '` even returned 0 for exactly this reason — the lines
were indented and joined. The hosted pg_prove lane is the one that parses the
stream. That is the honest gap in round 1's evidence.)

## Fix

Every assertion is now its own statement — the repo's existing pgTAP style
(`health_metrics_precedence.sql`, `purge_sync_generation.sql`):

- GREEN: the single merge call asserts the returned `group_id`; `duration`,
  live-recording `count` and `note` are asserted from the row/recording state
  they were written to (one statement each). The multi-column warning is
  recorded in a comment so it is not "simplified" back.
- RETRY: the two returned columns are asserted in two statements, each its own
  replay call (replaying more than once is the point of the block).

No assertion was deleted or weakened: the file still asserts cross-account
rejection under a real `set local auth` role switch (tests 3–8, 36),
same-day/type/survivor/degenerate guards (9–13), atomic rollback of the
re-point + deletes (14–17), the GREEN merge values (18–30) and RLS (34–37).
