## Blocker 1 — the tooltip card clipped its own wrapped text (AC2)

**Mechanism, verified on the reviewed head's own capture.** Row-classified
pixels of `training-load-axis-929-populated-ax5-light-selected.png`: last text
row **1000**, card's last border row **991** — the card's bottom border runs
through the `prior wk` glyphs. Cause: `TrainingLoadTooltip.swift:27` ended in a
plain `.fixedSize()`, which measures the content's **unwrapped** ideal; the
delta line wraps to a second line at `.accessibility5` (bounded by the call
site's `.frame(maxWidth: maxWidth)` at `TrainingLoadSheet.swift:435`), so the
background — sized to the one-line ideal — came up one line short. The suite
could not see it: `TrainingLoadAxisLegibilityTests` measured the *slot reserve*
against the content and never the *card background* against the text.

**Exact change** (`TrainingLoadTooltip.swift`, one modifier, one file):
`.fixedSize()` → `.fixedSize(horizontal: false, vertical: true)` — wrap at the
proposed width, take the height the wrap needs. Every call site keeps its own
width bound, so `ActivityMixBar` and `SendConditionsDetailSheet` are unaffected.

**Measured after the fix** (rendered pixels, light scheme):

| render | card border row | last text row | contained |
|---|---|---|---|
| tooltip chrome, default (375 pt, 2×) | 149 | 116 | yes |
| tooltip chrome, `.accessibility5` | 530 | 492 | yes |
| the real weekly card at `.accessibility5` (`fix-tooltip-card-ax5-section.png`) | 1094 | 1059 | yes |
| re-captured offscreen selected section at the fixed head | 1094 | 1059 | yes |

**Second-order repair the fix exposed.** With the card finally sized to its
wrapped content, `WeeklyBarsView` composes a tooltip that measures **258.5 pt**
at `.accessibility5` — larger than the ≈221 pt the shipped 60 pt reserve base
provided. The base grew 60 → **72** pt, and the reserve test now walks **all
twelve** Dynamic Type sizes against the measured tooltip (tightest slack
**4.0 pt**, at the default size). That under-reserve was invisible before
because the old test measured a layout probe (199.5 pt), not the tooltip the
view actually composes.

## Blocker 2 — the app drew the readout *and* every value label

**Determination (the brief demanded one): neither a stale build nor a harmless
transient — the reviewed head's width channel is *stably* wrong in the app.**

1. The reviewed head was rebuilt unchanged, installed on a **fresh** iPhone SE
   (3rd generation) simulator (`impl929-fix-sim`,
   `F9FF4E5A-1D22-486A-AB41-3E34B0E625F2`) and launched with the existing
   `--training-load-fixture` argument at the default text size: the weekly card
   carried the four `2,640 / 2,400 / 2,280 / 2,670` labels **and** the
   `3w 2,640 AU …` list. Reproduced, not just reported.
2. Temporary instrumentation (reverted; the sheet is byte-identical to the
   delivered blob `581ece17…`, `git diff` empty) printed the numbers:
   `diagnostic-app-width-probe.png` + `diagnostic-marker-*.png`. The chart's own
   reader reports **311**, while **all three** width channels — the in-reader
   `PreferenceKey`, a second key set from the same closure, and an outer
   background reader — deliver **41**, and `onPreferenceChange` fires exactly
   **twice**: the settled width (311) never reaches the state, so the readout's
   plan is computed at 41 pt (no label fits) while the chart draws from 311 pt.

**Exact change** (`TrainingLoadSheet.swift`): the readout's width is now read by
the background-`GeometryReader` pattern the codebase already ships —
`ContributionHeatmapView.swift:99-105`:

```swift
.background(
    GeometryReader { proxy in
        Color.clear
            .onAppear { containerWidth = proxy.size.width }
            .onChange(of: proxy.size.width) { containerWidth = $0 }
    }
)
```

The deleted `ChartWidthKey` preference was the only reason the two plans could
disagree: the readout now resolves from the same width the chart's in-reader
plan draws from.

**Serving model (what actually serves the width on this host).** The width is
served by the background reader's `onAppear` / `onChange(of: proxy.size.width)`
callbacks; the `PreferenceKey` channel is **not** serving — it delivered the
first layout pass's placeholder width (41 pt) and never delivered the settled
one. The fix removes the dependency instead of trying to out-schedule it.

**Pixels, before → after (the same fixture, the same simulator, default size):**

| | labels drawn | readout drawn |
|---|---|---|
| reviewed head (`issue-929/simulation-929-populated-normal-*.png`) | yes (4) | **yes** |
| fixed head (`issue-929-fix/fixed-populated-normal-*.png`) | yes (4) | **no** |

At `.accessibility5` the fixed head shows the opposite coherent state: no value
labels, and the exact-values list carries them (below the SE fold, as before —
the offscreen renders and the tests carry that view).
