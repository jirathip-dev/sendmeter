**Which launch-chain call performs the app-group access?** The one our code contributes is
`try? session.updateApplicationContext(payload)` — `Sources/Platform/WatchConnectivityService.swift:244`
(`transmitContext`, reached from the auth bootstrap's watch relay). The CFPreferences read/write itself is
inside **Apple's** `-[WCSession storeAppContext:withAppContextData:]`, which persists the application context
into the app-group container; `kCFPreferencesAnyUser` + a container is the framework's own CFPreferences
usage. The container lookup immediately before it **succeeded** (sandbox extension consumed).

**Does our own read produce it?** No. Our read sites are `ReadinessWidgetStore.appGroupStore`
(`native-plugins/sendlog-health-core/Sources/SendLogHealthCore/ReadinessWidgetContract.swift:158-161`),
consumed by `Sources/App/ReadinessWidgetBridge.swift:23,38,48` (app process) and
`Sources/Widgets/ReadinessWidget.swift:62` (widget extension). On the launch chain the app-process access is
`becameActive()` → `publishReadinessWidgetSnapshot()` → `ReadinessWidgetBridge.publish/clear`
(`AppModel.swift:1177`, `:1233`). If that access emitted the CFPrefs error, the capture would show a
**second** occurrence later in each launch (after auth resolves, not ~80 ms after process start). It does
not: there are exactly 4 occurrences, each inside the WC sequence.

### 1.2 What the app-group read actually does (measured, app process, real entitlement)

New app-target suite `ReadinessWidgetAppGroupReadTests` (3 tests, all green in the focused run and the
full CI-shape run):

- `testAppGroupReadReturnsTheStoredPayload` — `ReadinessWidgetStore.appGroupStore` is non-nil in the app
  process; `save(snapshot)` → `load() == snapshot`; a second store over the same suite sees the same
  payload; `clear()` → `load() == nil`. **The read returns the stored payload.**
- `testAppGroupPublicationPathLandsInTheReadableContainer` — the production path
  (`ReadinessWidgetBridge.publish(snapshot, for: NativeAccountScope(userID:epoch:))`) lands in the same
  container and reads back; `ReadinessWidgetBridge.clear()` removes it.
- `testAppGroupReadOfAnUnavailableSuiteIsANilReadNotAnError` — a suite this process holds no entitlement
  for still round-trips *inside* the process and is **not** visible through the app group; a suite with
  nothing stored reads as `nil`. The failure mode is a **nil read**, never a throw: `load()` is
  non-throwing by signature, and every consumer uses optional chaining (`store?.load()`,
  `guard let store = … else { return }`), so an unavailable/detached container degrades to "no snapshot"
  — a silent no-publish. There is no error on this path for the banner to catch.

### 1.3 Verdict

- The app-group CFPrefs line is **not the banner's cause**: it is a framework-internal CFPreferences
  detach inside WatchConnectivity's app-context persistence, it does not throw into app code, and our own
  call site swallows its error with `try?` anyway.
- Our app-group read is **not broken** — it returns the stored payload and its failure mode is a nil read.
- **Change nothing in the app-group read path** (per the orchestrator's clarification: evidence first,
  minimal change; no fix where the read returns correctly).

## 2. Classification — the launch-path load funnel (AC2 / AC3)

### 2.1 The mapping table

| error family (launch-path load) | old | new |
|---|---|---|
| `DeltaReadError.outOfOrderPage` / `.cursorDidNotAdvance` / `.pageBudgetExhausted` (the delta reader failing closed) | `.unknown` | `.dataUnreadable` |
| `CacheUnavailableReason.noSupportDirectory` / `.openFailed` (cache preparation at launch) | `.unknown` | `.cacheUnavailable` |
| `URLError` code the taxonomy does not name (`badServerResponse`, `cancelled`, `cannotParseResponse`, …) | `.unknown` | `.loadFailed` (via the load funnel) |
| any other error the taxonomy cannot attribute, on the **load** path | `.unknown` | `.loadFailed` |
| `BackendFailureReason.unknown` reached from a load | `.unknown` | `.loadFailed` (via the load funnel) |
| everything the taxonomy already names (`DecodingError`, GRDB, `LocalCacheError`, `DurableQueueError.invalidDirectory`, `NSOSStatusErrorDomain`, `HKError` families, `URLError` mapped codes, `PostgRESTError`, `AuthError`, …) | unchanged | unchanged |

New class + copy (`Sources/Core/FriendlyError.swift`):

```
case loadFailed   →  "Sendmeter couldn’t load your data. Try again."
```

The funnel is `UserFacingError.classification(forLoadFailure:)` / `message(forLoadFailure:)`
(`FriendlyError.swift`), applied at the refresh funnel's two failure sites
(`AppModel.recordPartialRefresh` and `refreshAll`'s catch) for **both** the banner copy and the
Dashboard's retained `dashboardLoadFailureClass`, plus the scoped failure row's `reason`. The raw
classifier (`classification(for:)`) is unchanged, so non-load callers (e.g. internal queue invariants)
still get `.unknown` where that is the honest answer — `.unknown` is unreachable **from the load path**,
not from the whole app.

## 3. Logging uplift — the failure names itself

`AppModel.swift`, `Logger(subsystem: "com.jirathip.sendlog.native", category: "launch-failure")`, level
`.notice` (persisted by default — the capture proved `.info`/`.debug` app messages are not persisted):

```
launch failure step=<STEP> domain=<NSError.domain> code=<NSError.code> class=<FriendlyErrorClass>
```

| site | step name |
|---|---|
| `refreshAll`'s catch | `refresh` |
| `recordPartialRefresh` | `refresh-slice:<RefreshSlice.rawValue>` |
| `applyPreparedCache` failure | `cache-prepare` |
| `surface(_:)` (every banner) | `banner` |

**Privacy argument:** the line carries exactly three fixed-vocabulary fields — the step name (a literal),
the error's domain and numeric code (identifiers: `SendmeterCore.DeltaReadError`, `NSURLErrorDomain`,
`GRDB.DatabaseError`, `com.apple.healthkit`, `SendmeterNative`, …), and the taxonomy class. No
`localizedDescription`, no payload, no token, no user content, no server body is ever interpolated — which
is why `privacy: .public` is safe here and the line is readable in a device transcript. The `class` field
is the **raw** taxonomy result on purpose: an `.unknown` there is the signal that the taxonomy still lacks
a class for the real failure.

**Does it name itself on device?** See §5 (device leg).

## 8. The serving mechanism (runtime), and the model axis

- **Runtime mechanism that serves the fix:** the refresh funnel (`AppModel.refreshAll` catch /
  `recordPartialRefresh`) classifies through `UserFacingError.classification(forLoadFailure:)` and sets
  **both** the banner copy (`errorMessage`) and the retained Dashboard class
  (`dashboardLoadFailureClass`, which `DashboardView` leads with when no authoritative snapshot exists);
  the same funnel emits the persisted `.notice` line. Deliberately NOT load-bearing: the dismissible
  banner (`errorMessage`) — the Dashboard's retained class outlives it, and `ReadinessWidgetBridge`'s
  app-group access, which is a no-publish on failure and never a banner.
- **Model axis:** the lane's model is profile/registry-owned and is not named in lane reports (fleet
  policy); no config was changed by this lane.
