## 3. Root cause — the fence raced an app-owned pipeline (two stages)

The fence's old precondition was "the offline save has published its recording", polled in a 15s wall-clock budget. That publication has **two** app-owned asynchronous stages around the save, either of which can be in flight on a cold runner:

1. **Store open.** `saveForceSummary` publishes the recording locally (`cacheUpsertLocal` marks the pending row, `AppModel.swift:4516`; `insertPendingRecording` + `mergeRecordings` publish in memory, `:4531/:4533`), but the local write silently no-ops until the store's preparation flight has opened it (`guard let cachedWorkspace else { return nil }`, `:2343`). Every lifecycle entrypoint joins that flight via `prepareCacheIfNeeded()` (`:2680`; the account bootstrap itself does, `:1971`), and the runner line `step=cache-prepare … cacheUnavailable` from attempt 1 corroborated exactly this failure mode.
2. **The bootstrap's refresh pass straddling the save.** The pass re-derives the published list **from the store** (`recordings = snapshot.recordings`, `:2216`; pending-overlay rebuild `:2230`). If its cache read happens **before** the save's local write and its assignment **after** the save's in-memory merge, it republishes a list **without** the row — and offline nothing republishes it. This is the mechanism by which `recordings=[]` persisted for the full 15s on CI.

A v1 of the fix (store-join only) was applied and locally verified, then **failed on an erased-container run** (`app-tests-07-erased-full.log`, EXIT=65, `:133`/`:178` `recordings=[]`) — i.e. **stage 2 reproduced deterministically locally, producing the exact CI symptom**. The final fix closes both stages.

## 4. The fix (final shape) — publication is a deterministic consequence of actions the test takes

All in the fence's setup (`ForceLockOrphanAppTests.swift`, test at `:42`):

1. **Install the offline stub** (every request → HTTP 500), then `await model.prepareCacheIfNeeded()` + assert `model.cacheReadiness.isReady` — the same preparation flight every lifecycle entrypoint joins, so the save's local write cannot no-op.
2. **Settle the bootstrap pass the harness's own seeded session starts**: `waitUntil("the account bootstrap's refresh pass to finish", isSatisfied: { model.lastPartialRefreshFailure != nil || model.dashboardLoadFailureClass != nil })`. The offline stub guarantees that pass fails every slice, and the failure record is written only **after** that pass has published (`recordPartialRefresh` runs after the publication block, `:3394+`) — so once observed, no pre-save cache read remains unassigned.
3. **Save (offline) + identify the new durable row** from the queue file by its recording payload case — the identity that crosses durable row, published recording and device bookkeeping.
4. **Drive the publication the test owns**: `await model.refreshAll(showSpinner: false)` over the store the save wrote. Its hydration reads the store **after** the save's local write, so the store-backed list it publishes carries the pending row; and because every later pass reads that same store, the row is stable from here on — no deadline is involved.

The fence's own precondition now contains **no wall-clock budget**: the two inline 15s waits are deleted; the only deadline left in the test is the file's standard 60s `waitUntil` bound on the (deterministic-to-occur) bootstrap settle, and the harness's pre-existing auth-sign-in wait (untouched, part of the shared harness).
