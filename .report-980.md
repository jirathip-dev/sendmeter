## 2. Product answer: carrying the new bearer is NOT acceptable — refuse it at credential selection

Arguing from the code that owns credential selection:

* **Credential selection has exactly one seam.** `AuthService.ensureFreshSession()` is documented as
  "The ONE token-bearing seam… so the access token is never read off a possibly-expired session", and
  `PostgRESTClient(sessionProvider:)` calls it per request. It selects whatever session the SDK
  stores, with no notion of which account the app publishes.
* **The SDK stores before the app processes.** supabase-swift's session is authored at sign-in; the
  app learns about the boundary later, on the serial `authStateChanges` loop. So for the window the
  two notions of "account" disagree: the credential is B's, the published account is A's.
* **The #933 fences do not cover this boundary.** `AccountScopedFetch.canApply` gates *publication of
  a completion* against `(currentUserID, accountEpoch)`. In the reproduction the crossing **completed
  after** the model had moved to B, so its completion legitimately looked like B's own work and was
  applied — `queueCount(for: A) == 0` at base, i.e. A's intent was acknowledged by an operation that
  executed under B's identity (the backend would have written/read it as B, RLS and all). The fence
  cannot un-execute a request that was already shaped with the wrong credential.
* **So the failure is not "stale data published late" — it is "work executed in the wrong
  account"**, the exact class both #933 and #980 exist to prevent. It is not acceptable to let it
  through and rely on fences at the end.
* **Alternatives rejected:** *cancel in flight at the boundary* — no cancellation token reaches the
  sessionProvider, and cancellation can't undo a request that already applied; *keep/send A's old
  bearer* — impossible by design (single-holder rule, #265: nothing here stores or relays a token,
  and the SDK has replaced it anyway); *block sign-in until the loop drains* — couples the UI to an
  unbounded queued network await. **Refusing the credential and failing the caller's work retryably**
  is the minimal, design-consistent answer: the work stays owned by A, the queue keeps its plain
  backoff (the refusal is deliberately not an `AuthRecoveryError`/`ServerRejection`, so nothing is
  cleared, no quarantine budget is spent), and it re-runs under its own account once the boundary
  lands. That is the behaviour the GREEN receipt shows (`refusedLocally=["queue-upload:preset"]`,
  A's item still owned by A, `crossed=[]`).

## 3. Chosen outcome: close the window at the credential-selection seam (production change)

* `Sources/Data/SupabaseService.swift:49` — `AuthCredentialWindowRefusal` (plain `Error`, carries
  both account ids; NOT a recovery/rejection type: no sign-out, no clear, no quarantine).
* `Sources/Data/SupabaseService.swift:91` — `AuthService.publishedAccountUserIDProvider`
  (internal; `nil` = no published identity to enforce, e.g. bare `AuthService` in tests/previews →
  check inert).
* `Sources/Data/SupabaseService.swift:156` and `:193` — both `ensureFreshSession` return points (fast
  path + post-refresh path) pass through the new `requirePublishedAccount` (`:220`), which throws the
  refusal when the selected session's user id differs from the published account. Synchronous: the
  provider reads live `@MainActor` state with **no await between selection and check**.
* `Sources/App/AppModel.swift:1110` — the one wiring site: `auth.publishedAccountUserIDProvider =
  { [weak self] in self?.currentUserID }`, i.e. the same value the #933 fences read.

**Why this cannot break the boundary's own bootstrap:** in `handleAuthEvent`, the signed-in branch
publishes `authSession = session` (AppModel.swift:2002) *before* it touches the network with that
session (`refreshAll` :2031, `drainQueue` :2038, `relayValidSessionToWatch` :2196) — so by the time
the new account's own work calls the seam, `currentUserID` already equals it and the check allows.
Only work belonging to the outgoing account — the window's actual inhabitants — is refused. The
pre-existing `relayValidSessionToWatch` guard (`valid.user.id == userID`, :2200) is the same rule
applied at the watch relay; this change generalises it to the seam that can't just skip silently.

No auth guard was weakened, no assertion weakened, no tolerance widened, no `-skip-testing`, no
retry-into-green, no sleep-as-fix. `Package.resolved` churn from xcodebuild was reverted (brief rule).
