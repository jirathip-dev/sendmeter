Re-derivation (#991):

* Four cold launches, four occurrences — one refused source per process, on
  the same thread as the app's own WatchConnectivity relay call, 1-3 ms
  after `-[WCSession updateApplicationContext:error:]_block_invoke size: ...`
  and `storeAppContext:`.
* Between the relay and the refusal, the SAME thread (169bb1/16c19a/16c621/16cf45)
  runs the app-group container lookup: `container_create_or_lookup_app_group_path_by_app_group_identifier`
  -> `Consumed sandbox extension` -> `success`. Apple's WatchConnectivity
  framework does not reference CFPreferences, UserDefaults, suite APIs or the
  app-group container API (see 991-mechanism.txt), and its own persistence
  work runs on its own queue (169be3 in launch 1: `foundation.filecoordination:presenter`).
  So the container lookup and the refused source are created by this app's
  own code on the callback thread.
* The signed-out relay (UA size 67, launch 1 line 244 / launch 2 line 24789)
  is followed by no app-group access at all: after it, no container lookup
  and no refused source. The app-group access only follows the SIGNED-IN
  relay, i.e. the branch that reaches `resetAccountState()` ->
  `ReadinessWidgetBridge.reset(for:)` -> `ReadinessWidgetStore.appGroupStore`
  (health-core `ReadinessWidgetContract.swift`), the first app-group suite use
  of the process.
* Later relays in the same process (launch 1 line 571 onward) show no
  additional refused source: cfprefsd refuses the AnyUser source once per
  process and the source then serves in direct mode.
