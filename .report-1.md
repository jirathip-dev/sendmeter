## The actual serving model (runtime mechanism)

"Workspace refresh and reconciliation" are served by **one `SendmeterCore` owner
plus explicitly passed boundaries** — not by a view, a per-call-site helper, or
an `AppModel` extension:

* **`WorkspaceSyncCoordinator`** (`Sources/Core/WorkspaceSyncCoordinator.swift`)
  owns five shared rules: (1) the fetch plan
  (`WorkspaceRefreshPlan.cursor(for:)` / `appliesFullSnapshot(for:)`, `:103-134`),
  (2) the optional purge-generation endpoint and its fallback
  (`resolvePurgeGeneration`, `:287`), (3) one entity's full-vs-delta reconcile
  (`reconcileEntity`, `:371`), (4) one targeted slice's
  cursor → fetch → boundary re-check → reconcile → publish-read sequence plus the
  cache-unreadable degradation (`reconcileSlice`, `:414`; the background engine's
  per-entity form is `backgroundOperation`, `:479`), and (5) the per-slice
  outcome collection that decides which consistency groups may publish
  (`collectOutcomes`, `:261`).
* **The store is the app's existing one.** `WorkspaceSyncStoring` (`:18`) has
  exactly one production conformance — `extension CachedWorkspace:
  WorkspaceSyncStoring` (`:49`) — so there is no second cache handle, no second
  cursor store and no second sync owner. `CachedWorkspace.swift:97-105` records
  that #922's second read entry point (`CacheHydrator.coherentRead`) was deleted
  with the extraction, leaving exactly one coherent-read path.
* **`AppModel` keeps composition and feature-facing state**: which repository
  method fetches which entity, the account/epoch capture and completion token,
  the publication closure and the published collections, freshness stamps,
  banners and the durable-queue restore. Its refresh/reconcile algorithms are
  gone; what remains are delegators that supply the open store handle and the
  diagnostics sink (`AppModel.swift:2183-2232`, `:2713-2722`).
* **Store work stays off the main actor**: the coordinator performs every store
  call through `CacheOffload.run` (a detached task), exactly as the extracted
  code did — the #922 read instrumentation
  (`cacheSnapshotReadCount`, `lastCacheSnapshotReadOnMainThread`) still counts
  one refresh as exactly two full-workspace reads.
