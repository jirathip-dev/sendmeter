## Cursor format (documented)

Persisted in `sync_cursors.cursor`, documented next to the reader in
`Sources/Core/DeltaCursor.swift`:

- **Composite (current)**: `<timestamp>|<entity-id>`, e.g.
  `2025-10-09T08:53:20.000000Z|00000000-0000-0000-0000-000000000002`.
  `<timestamp>` is exactly `LocalCacheStore.syncCursorString(from:)` (fixed-width
  UTC microseconds, so text order == chronological order); `<entity-id>` is the
  row's stable cache entity id (the row's `id` for sessions/recordings).
- **Legacy (pre-#914)**: a bare `<timestamp>` with no separator. It carries no
  tie-break, so the next read re-fetches the whole tie group at that timestamp
  (`updated_at=gte.<stamp>`) instead of skipping the rest of it. Re-reading is
  safe — a delta upsert is keyed by entity id.
- **Unparseable**: treated as "no cursor" → a full re-read, never a partial one.

Per-page query (`DeltaPageQuery`): `order=updated_at.asc,<tie-break>.asc`,
`limit=<pageSize>`, plus

- composite cursor:
  `or=(updated_at.gt.<stamp>,and(updated_at.eq.<stamp>,<tie-break>.gt.<id>))`,
- legacy cursor: `updated_at=gte.<stamp>`,
- no cursor: no filter (first sync).

### AC2 — deterministic capped-response fixture >2 pages, duplicate retries, same-timestamp rows; every expected ID reconciled exactly once logically — **PASS**

- `CappedDeltaServer` (cap 2, requested page size 2, 11 rows) and
  `CappedPostgRESTPager` (cap 3, requested page size 500, 8 rows) are both
  deterministic PostgREST-shaped pagers that parse the client's `order`, `limit`
  and cursor filter and throw on a malformed query (a broken query contract
  fails the test instead of passing silently).
- Duplicate retry: `testDuplicateRetryReconcilesTheEntityOnceWithItsLatestRevision`
  re-stamps a row that was already served after page 2; the fixture asserts it
  really served that id twice (`servedIDs` count == 2), then asserts the delta
  contains it **once**, with the latest revision (`updatedAt == T5`,
  value == v2). The transport-level fixture does the same through
  `URLProtocol` (row 2 re-served after page 1).
- Exactly-once: `changes.count == 11` with `Set(ids).count == 11` (reader test);
  `changes.count == 8` with `Set(ids).count == 8` (transport test).
- Same-timestamp rows: T1 holds 4 rows in the transport fixture, 3 in the reader
  fixture, both split across a page boundary.

### AC3 — a failed/cancelled middle page does not become an authoritative snapshot, delete unseen cached rows, or advance the checkpoint — **PASS**

- Reader: `testMiddlePageFailureThrowsAndNeverReturnsADelta` — the page-2
  transport error propagates, no delta is returned, the run stopped at page 2.
- Cache: `testMiddlePageFailureLeavesCachedRowsCheckpointAndBoundaryUntouched` —
  after a first sync of 4 rows, a second read whose page 2 fails leaves the
  cached snapshot **byte-equal** (`XCTAssertEqual(before, after)`), the
  checkpoint string unchanged, `hasCompletedSync` unchanged, and the unseen new
  row absent. The fixture's page 1 omits two cached rows and carries two new
  ones, so a partial read treated as authoritative would tombstone rows 1–4 —
  proven to happen under the RED splice below.
- Transport: `testMiddlePageFailureThrowsInsteadOfReturningAPartialDelta`
  (HTTP 500 on page 2 → `fetchSessionDelta` throws, 2 pages served).
- Design: the reader returns a delta only after the last page; the cache applies
  changes first and writes the cursor afterwards (`CachedWorkspace.reconcileDelta`
  / `reconcileServerDelta` unchanged), so an interrupted read cannot advance the
  durable checkpoint.

### AC5 — pagination bounded per request and resumable; server row limits not raised; RLS/auth scope unchanged — **PASS**

- Bounds: `DeltaPageReader.defaultPageSize == 500` (below Supabase's default
  `db-max-rows` 1000) and `defaultPageLimit == 64` pages per run. The transport
  test asserts every request carried `limit=500`, and the reader test asserts the
  client never raises it (`["5","5","5","5"]` while the server capped at 2 rows).
- A server cap **below** the requested page size does not end the read: the
  client sends `Prefer: count=exact`, `PostgRESTClient.requestPage` parses the
  `Content-Range` total, and the reader keeps paging while
  `rows.count < totalCount` (or the page came back full). Proven by
  `testResponseCapBelowTheRequestedPageSizeStillConsumesEveryRow` (cap 2,
  pageSize 5, 7 rows, 4 pages) and by the transport stub (cap 3 < 500).
- Resumes safely: the durable checkpoint only advances after a complete read;
  an interrupted run keeps the previous checkpoint and re-reads from it
  (idempotent by entity id).
- No server change: `supabase/**` untouched, no migration, no config, no
  `max-rows` change. Auth/RLS scope unchanged: `performRequest` is the previous
  `request` body moved verbatim (same `apikey`, `Bearer` token from the session
  provider, `Accept`, error mapping); `requestPage` adds only `Prefer:
  count=exact` and reads a response header.
