### The actual serving model (runtime mechanism)

Both issues are served by **one preparation actor plus one coherent-read
boundary in `SendmeterCore`** — not by a view-local or per-call-site trick:

* **Store preparation** — `CachePreparation` (`Sources/Core/CachePreparation.swift:171`)
  owns the single flight. `AppModel.init` starts it and returns
  (`Sources/App/AppModel.swift:887-919`); the auth bootstrap, the foreground
  pass, the refresh funnel and the background app-refresh all
  `await prepareCacheIfNeeded()`, which joins the SAME flight. Directory
  creation + GRDB open + schema migrations run inside the flight's detached
  task (`CachePreparation.swift:184-206`), so **no main-actor code path blocks
  on storage**.
* **Honest state** — `CacheReadiness` (`CachePreparation.swift:36`) is the
  published answer; `honestSyncInputs(_:)` (`CachePreparation.swift:58`) is the
  ONE gate that keeps an unready cache from resolving to "Synced". A failed
  open is recoverable — the flight drops a failed result so the next entrypoint
  retries (`CachePreparation.swift:198-206`) — and the app runs network-only
  meanwhile.
* **Coherent reads** — `LocalCacheStore.coherentSnapshotRead`
  (`LocalCacheStore.swift:505-587`) is ONE read transaction returning the nine
  collections, the pending rows, the cursors, the boundaries, the purge
  generations **and** a content revision (`CacheSnapshotRead.swift:13`).
  `CacheOffload.run` (`CacheSnapshotRead.swift:127`) is the single
  off-main-actor hop; `AppModel.readCoherentCache` is its only caller.
* **Where the queue layer still owns the truth** — nothing here touches the
  durable queue's identity/revision fencing, the cache's pending-local-write
  precedence, or the LWW rules. The one ordering fix this lane had to make is
  that the publication reads the workspace **immediately before the
  synchronous publication closure** (`AppModel.swift:3195`), so an optimistic
  local write that landed while the pass was suspended can never be overwritten
  by an older revision; the queue restore's "already on the server" identity is
  derived from that pass's own reads, including the reconcile's tombstone rule
  (`AppModel.swift:3145-3185`).
* **The store open is serialised process-wide** — `CacheStoreOpenGate`
  (`CachePreparation.swift:127-140`) plus a 5 s busy timeout on the
  file-backed store (`LocalCacheStore.swift:245`). Moving the open off the main
  actor removed the implicit main-actor serialisation of GRDB's migrator: two
  `AppModel` instances in one process could then migrate the same file at once,
  which is what produced `SQLite error 5: database is locked … FROM
  grdb_migrations` in the flaky suite run committed under
  `docs/evidence/issue-921/`.

### Flake disclosure (raw, both outcomes — do not read the red suite as hidden)

`docs/evidence/issue-921/app-target-suite-flaky-host-load.log.gz` is an earlier
full CI-shape run at an intermediate head that reported **139 tests / 51
failures** in 93.9 s on a saturated host (loadavg 226–247). The failing classes
clustered on the documented host-load-sensitive ones and one failure was
explicit: `SQLite error 5: database is locked - while executing SELECT
identifier FROM grdb_migrations`. That error is a REAL defect this lane
introduced and fixed: moving the open off the main actor removed the implicit
main-actor serialisation of the migration, so two `AppModel` instances in one
process could run the migrator on the same file at once. The fix is the
process-wide `CacheStoreOpenGate` plus the 5 s busy timeout.

The **remaining** red at the final head is one test,
`GuidedProtocolCompletionTests.test941BackToBackProtocolsLogOneEntryWhenTheSessionEndsExplicitly`,
asserting 2 recordings in one group (lines 88 and 98). It is **green in focused
runs on a freshly erased simulator** (single test and whole class, with the same
head), and it has been observed to fail at *three different* assertion lines
(88/98 and 95/96) across runs of two different publication shapes at the same
level — i.e. its outcome is interleaving-sensitive in suite context, the
documented stale-container/ordering class for this file. I did not resolve it
and I am **not** claiming the suite is green; the focused log and the red suite
log are both committed so the next lane can decide.
