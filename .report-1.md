### In-lane defect found and fixed (worth the reviewer's attention)

The first implementation keyed the queue item by a UUIDv5 of the row DATE alone. The
queue is ONE shared file for the whole device, and `DurableQueue.enqueueIfCurrent`
matches items by id BEFORE it checks the account: a pending health write for today
under account A therefore made account B's health write for the same day
**un-enqueueable** (three silent retries, then "This change couldn't be saved on this
device"). It was caught by the app tests on a container that still held an earlier
run's item, reproduced in isolation, and fixed by making the account part of the key
(`queueItemID(for:accountUserID:)`). `HealthWriteIdentity` has a discriminating unit
test for it, and the app tests now construct an account-scoped fake so this class of
cross-account interference can never pass unnoticed again. The pre-existing
`phaseTransition` singleton key (`91700000-…-917`) has the same cross-account property;
it is **out of this lane's fence** and is called out here rather than changed.

## What I did NOT verify

- **A real process kill (SIGKILL).** "Process death" is modelled by constructing a fresh
  `AppModel` over the same on-disk cache + queue (the #916–#918 convention). No actual
  `SIGKILL`/crash-recovery run was performed.
- **Real HealthKit.** All app-target runs use the internal `metricsReader` seam (the seam
  this lane added to `Sources/Platform/HealthKitService.swift`, as the fence allows). A
  genuine HealthKit read, the authorization flow and background delivery were not
  exercised. The seam is the only Platform change and replaces ONLY the read.
- **Disk failure / queue-unavailable path.** "No durable intent ⇒ the pass fails loudly
  and writes nothing" is covered by code inspection and the shared
  `surfaceDirectWriteNotPersisted()` path, but no test forces a failed queue write (the
  AppModel queue is created in `init` and has no injection point inside this fence).
- **Device / TestFlight behaviour, hosted CI, a live Supabase project.** All evidence is
  against a stubbed PostgREST whose health endpoints model the migration's semantics
  (`resolution=ignore-duplicates` insert-if-missing, the precedence RPC's coalesce
  merge, `real` columns). No live database, no device, no release build.
- **The residual in-flight recovery race.** If a NEWER pass for the same date lands
  while an older recovery's write is already on the wire, the older payload still
  reaches the server (last-writer-wins at the RPC, the same property the live path has).
  The local revision fence keeps the newer local state intact
  (`testInFlightRecoveryDoesNotClearANewerLocalRevision`), and the recovery does
  re-check the server's row before deciding — but the window between that check and the
  write is not closed. Closing it would need a server-side compare-and-set on
  `computed_at`, which is outside this issue's fence and not requested by it.
- **The cross-account residue of the fixed-account `94000000-…-940` test suites.** Those
  suites share one persisted container account; a dirty container from an earlier local
  run makes `GuidedProtocolCompletionTests` fail (attempt 1 above). A freshly erased
  simulator is required for a clean local run; hosted CI always starts fresh.
