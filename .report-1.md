### The actual serving model (runtime mechanism)

Account isolation for an in-flight refresh/save is served by **one publication
fence evaluated at each publication point**, fed by a process-serial auth-event
loop — not by cancelling in-flight work, and not by a per-view check:

* **The fence** — `AccountScopedFetch.canApply(to:accountEpoch:)`
  (`Sources/Core/AccountScopedFetch.swift:16`) compares the *live* account id
  **and** the lifecycle epoch against the values captured before the async work;
  `publishIfCurrent` (`:26`) runs the publication closure only when it passes.
  `AccountScopedCompletion.owns(...)` (`:50`) adds the same-account **token**, so
  an older completion cannot finish a newer request.
* **The epoch** — `AppModel.resetAccountState()` (`Sources/App/AppModel.swift:12428`)
  advances `accountEpoch` at every account boundary (sign-out, changed user,
  auth self-heal) and clears the visible snapshot in the same synchronous
  boundary. It is reached from `handleAuthEvent` (`AppModel.swift:1844`), fed by
  the SDK's own `authStateChanges` loop (`AppModel.swift:1018-1023`).
* **The call sites that publish** — the refresh funnel: pre-publication guard
  `AppModel.swift:3053`; the single publication closure `AppModel.swift:3229`
  (`publishIfCurrent` → `mergeSessions`/`mergeRecordings`); the partial-failure
  summary `AppModel.swift:2869` and its Dashboard class `AppModel.swift:2845`;
  the cache-hydration read fence `AppModel.swift:2120`; the queue-count
  publication `AppModel.swift:11212` (earlier guards `:11194`/`:11207`); the
  durable-write upload fences `AppModel.swift:9795` (entry), `:10503` (preset),
  `:9895` (session), `:10666` (acknowledgement + queue removal).
* **What deliberately is NOT the mechanism** — the credential a request carries
  is the *live SDK session* (`PostgRESTClient.sessionProvider` →
  `AuthService.ensureFreshSession`, the production wiring at
  `AppModel.swift:856-863`), so the fence is what keeps A-owned work from being
  re-sent after a switch; and a rejected bearer's self-heal is **exact-session**
  (`SupabaseService.swift:301` `recoverFromAuthFailure`, using the
  `PostgRESTError.sessionDescriptor` captured per request at
  `SupabaseService.swift:911`), so an old account's 401 cannot clear the new
  account's session. Both are asserted; neither is a substitute for the fence.

### Test shape (what is real, what is stubbed)

Every test signs in through the **real** Supabase SDK auth client
(`AppModel.signIn`/`signOut` → `authStateChanges` → `handleAuthEvent`), so the
account switch is the production boundary, and suspends a **real** repository
request inside the URLSession transport (`PostgRESTClient` with a URLProtocol
stub session; the transport's bearer comes from `AuthService.ensureFreshSession`,
i.e. the live SDK session). Stubbed: the network (URLProtocol), the auth storage
(in-memory `AuthLocalStorage`), the cache file (temp-dir `LocalCacheStore` via
`CacheStorageSeams`), the clock (`ServerClockStore`/`AuthSessionGuardStore` on a
private `UserDefaults` suite). No live backend, no HealthKit, no secret material,
no source-text assertion.

* **Device-only legs** — none claimed.
* **Realtime behaviour** — the stub answers the `wss://…/realtime/v1/websocket`
  upgrade with an HTTP response, so the SDK's realtime join fails best-effort
  (five bounded retries) exactly as in the other app-target suites. The realtime
  path is not covered by these tests; the harness's bootstrap waits are generous
  because of those retries.
* **The pre-event credential window (OPEN, unscoped).** In one run that was
  invalidated by a harness bug (the hold released instantly instead of holding),
  a request was observed carrying the *new* account's bearer while the model's
  `currentUserID` was still the old account — i.e. the SDK stores the new session
  before the model's auth-event loop handles `.signedIn`. That window is not
  fenced by the model-side epoch/account fence these tests prove, and it is not
  reproduced by the delivered tests. Recorded as OPEN, not as a claimed defect.
* **Queue status is a witness, not a bite.** `refreshQueueCount` reads the
  *current* account's items (`AppModel.swift:11199`) before its fenced
  publication, so a stale completion cannot publish another account's count by
  construction; the delivered test asserts B's published count and B's on-disk
  item survive A's completion, but that assertion cannot be made to fail by
  removing the fence alone.
* **`just check-static`** was not run: it is pre-existing red at this base
  (`scripts/validate-native-static.sh` expects

## Host notes (this round)

* `DispatchTime + TimeInterval` adds NANOSECONDS: `.now() + 20` is a 20 ns
  timeout, not 20 s. The first harness iteration "held" nothing because of it.
* **A blocking `URLProtocol.startLoading` freezes every other stubbed request in
  the process**: CFNetwork services all custom protocols on one
  `com.apple.CFNetwork.CustomProtocols` runloop thread (proved with
  `sample <app-pid>`, committed in `sample-blocked-protocol.log.gz`). The
  delivered hold therefore *suspends* the request and answers it later from the
  test — which is what lets two passes/two accounts overlap.
* A `@MainActor` XCTest that blocks on a semaphore starves the very model task it
  is waiting for; every entry wait in this suite is an async poll.
* `PendingWrite` is app-model-private, so the queue is read as the raw
  `pending-writes.json`; a test's own items stay on disk keyed to that test's
  fresh account UUIDs (disclosed, and invisible to any other account).
* The test-hosted `AppModel` has no view hierarchy, so `bootState` never leaves
  `.loading` unless the test calls the production entry point
  `model.splashPresented(at:)` (`AppModel.swift:1042`). The harness calls it; it is
  a disclosed seam, not a production change (no production file is modified by
  this lane).
* Disclosure (seam added): **none**. No production seam was needed — every
  substitution used already-shipped seam (`AppModel.init` injections,
  `CacheStorageSeams`, `PostgRESTClient`'s session/sessionProvider, the SDK's
  `SupabaseClientOptions` storage/global-session).
