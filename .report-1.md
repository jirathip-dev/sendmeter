## Classification table (old → new)

| Failure family | Base outcome (`UserFacingError.classification(for:)`) | Head outcome | Copy at head |
|---|---|---|---|
| `DecodingError` (stored or received payload this build cannot decode) | `.unknown` → "Something went wrong while completing that. Try again." | `.dataUnreadable` (new) | "Sendmeter couldn’t read some of its data. Update Sendmeter, then try again." |
| GRDB `DatabaseError` (cache open/read/write), incl. the bridged `GRDB.DatabaseError` domain | `.unknown` | `.cacheUnavailable` (new); `SQLITE_FULL` → `.storageFull` (existing class) | "Sendmeter couldn’t read its saved data on this iPhone. Reopen the app, then try again." |
| `NSOSStatusErrorDomain` (Security framework / Keychain) | `.unknown` | `.secureStorageUnavailable` (new) | "Sendmeter couldn’t reach its saved sign-in on this iPhone. Reopen the app, then try again." |
| Supabase Auth SDK `KeychainError` (internal struct; bridges to `<Module>.KeychainError`) | `.unknown` | `.secureStorageUnavailable` | as above |
| HealthKit `HKError` domain `com.apple.healthkit`, codes 4/5/10 (authorization denied / not determined / required) | `.unknown` | `.healthPermissionDenied` (existing class) | existing copy |
| HealthKit codes 1/2/6/11 (data unavailable / restricted / database inaccessible / no data) | `.unknown` | `.healthUnavailable` (existing class) | existing copy |
| `LocalCacheError.invalidPayload` | `.unknown` | `.dataUnreadable` | as above |
| `LocalCacheError.invalidJSON` | `.unknown` | `.cacheUnavailable` | as above |
| `DurableQueueError.invalidDirectory` | `.unknown` | `.cacheUnavailable` | as above |
| `DurableQueueError.accountMismatch / .itemNotFound / .alreadyQuarantined` | `.unknown` | `.unknown` (deliberate) | generic fallback — internal invariants |
| HealthKit codes 3/7/8/9 (invalid argument, user cancelled, workout-session states) | `.unknown` | `.unknown` (deliberate) | generic fallback — not failures the app can explain honestly |

No mapping exposes a raw error, SQL text, `OSStatus`, or `HKError` identifier —
fixed copy per class, pinned by the leak assertions in `FriendlyErrorTests`.

HealthKit's domain/codes were **measured, not guessed**: `HKErrorDomain` is

## OPEN — the unreproduced device trigger (AC1/AC6)

- **What is open:** which operation on the launch-after-update path threw on the
  owner's device, and that error's real domain/code. The copy they saw proves
  only that it classified to `.unknown`; it does not name the operation.
- **Why it is open here:** the state that matters is the *pre-existing
  cache/session/queue from the previous build on a physical iPhone* plus a real
  launch-after-update. This lane has no device access, and simulator work cannot
  satisfy AC1/AC6 by the issue's own terms.
- **The exact measurement that closes it:** one device console capture — on the
  affected iPhone, install build 54 over the previous build, then capture the
  first launch with `Console.app` (or `idevicesyslog`) filtered to the app
  process, and record the **first logged failure with its domain/code**
  (`DecodingError` coding path, `GRDB.DatabaseError` result code,
  `NSOSStatusErrorDomain` code, `com.apple.healthkit` code) **and the operation
  that logged it**. With this taxonomy, that pair maps to a named class
  immediately — and for the four families above, to named copy instead of the
  generic sentence.
- **Not claimed:** any cause for the owner's screenshot. This lane does **not**
  claim the Dashboard was blank *because* the banner's failure happened; it
  claims only that (a) the failure families now have truthful classes and (b)
  the Dashboard can no longer present an unexplained empty screen behind a
  dismissed banner.
- **The stand-in the brief offered was not attempted**: crafting a previous-build
  cache/queue state on a simulator and driving the launch-after-update path. The
  malformed-payload failure this lane drives is a stub-level decode failure in
  the refresh funnel — a different artefact — and is not labelled as device
  reproduction.

## Serving model (what actually serves the behaviour at this head)

- The **refresh funnel** (`refreshAll`'s `catch` — the same funnel every
  bootstrap/foreground/retry pass uses) writes
  `AppModel.dashboardLoadFailureClass = UserFacingError.classification(for:)`;
  a refresh that reaches its authoritative-publication tail clears it, and
  `resetAccountState()` clears it at the account boundary.
- The **Dashboard render gate** is `AppModel.showsDashboardLoadFailure`
  (`failure != nil && !hasLoadedSessions && !hasLoadedRecordings` — the same
  last-good boundary `ErrorSurfacePolicy` reasons over), so a failure with
  last-good data on screen keeps the cards and only the banner speaks (#842
  preserved).
- The **retry** is `model.refreshAll()` — the same call that failed, run
  user-initiated; no bespoke reload path.
- The dismissible `errorMessage` banner is **not** load-bearing for the
  Dashboard state: clearing it leaves `dashboardLoadFailureClass` intact
  (pinned by `testFailedLoadClassifiesAndTheDashboardKeepsItsFailurePastDismissal`).
