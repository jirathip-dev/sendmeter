## What changed (and what deliberately did not)

The file's whole harness was written as **fixed iteration budgets**: four waits
of `for _ in 0..<600 { … try? await Task.sleep(nanoseconds: 5_000_000) }`
(~3 s nominal, no elapsed time and no state in the failure message):

| helper | old shape (at `fba3676`) | new shape (at `365615a`) |
| --- | --- | --- |
| `waitForQueueCount` (`:514`) | 600 × 5 ms, `queue never reached N; last observed M` | deadline `waitUntil` via `durableQueueState` |
| `waitForRecordedAttempt` (`:523`) | 600 × 5 ms, no state | deadline `waitUntil` via `durableQueueState` |
| `waitForFailureClass` (`:532`) | 600 × 5 ms, last class only | deadline `waitUntil` via `durableQueueState` |
| `waitForHeldRequest` (`:542`) | 600 × 5 ms, no state | deadline `waitUntil` via `holdState` |

- **One local helper, `waitUntil(_:timeout:isSatisfied:observed:)`**, polls the
  same way (5 ms) but is bounded by `ContinuousClock` against
  `waitDeadline = .seconds(60)` — 14× the worst hosted leg measured for this
  test (4.370 s) and ~50× its passing leg (1.180 s). It is implemented **in the
  test file**, not in a shared helper: the brief fenced shared helpers out
  (impl-920/PR #975 was editing `Tests/SendmeterNativeTests/`), and nothing
  shared was needed.
- **On expiry the diagnostic is the observed state + the elapsed time**:
  `queuedWriteCount`, `pendingCacheWriteCount`, the account id, every queued
  item's `kind`/`attempts`/`rejectionClass`, and the queue file a relaunch
  would read (`pending-writes.json` size + mtime, or `absent`). A slow runner
  and a broken durability path no longer produce the same line.
- **No assertion was touched.** The wait still requires the queue to reach its
  expected depth and the replay to still happen exactly once; nothing was
  skipped, loosened, or retried into green. Removed-vs-added lines over the
  whole file:

## The actual serving model (what the wait observes, and what does not serve it)

The value the wait polls is `AppModel.queuedWriteCount`. It is **published by
the queue-count refresh funnel**: `refreshQueueCount(for:)`
(`Sources/App/AppModel.swift:10641-10681`) reads the durable queue
(`queue.items(for:)`) and writes `queuedWriteCount` /
`queuedWriteDiagnostics` inside `AccountScopedFetch.publishIfCurrent` — i.e.
only when the account/epoch captured by the refresh is still current. The write
path the test waits on is `AppModel.switchPhase(to:)`
(`:3427-3487`) → `enqueueDirectWrite` (`:7901-8028`) → `queue.enqueueIfCurrent`
(`Sources/Core/OfflineQueue.swift:755`) → `refreshQueueCount` → publish; on a
stalled runner the item can be **persisted** (the file is on disk) while the
published counter has not been refreshed yet, which is exactly why the
diagnostic prints both the model's counts and the file's size/mtime.

Deliberately *not* load-bearing: the raw queue file itself (the wait never reads
it; only `queueFileContents()` does, when a test asserts persistence) and the
`queuedWriteDiagnostics` per-item view (it is a projection of the same
`queue.items(for:)` read that produces the count). The new `waitUntil` deadline
itself asserts nothing — it only decides when the observed-state report is
emitted.

## Contention demonstration: what the old budget actually was, and the pair that discriminates

Two things had to be measured before "the fix addresses the measured cause"
could be claimed.

**1. The old budget is not a wall-clock bound at all.** Its nominal value is
600 × 5 ms ≈ 3 s, but a poll whose sleep overshoots costs more than 5 ms per
iteration, so the *effective* bound is what the runner's scheduler decides. Measured
on this host with the durable path deliberately delayed *inside* the awaited
model call (in-call probe, `probe-inject4.diff` / `probe-inject2.diff`):

| leg | delay before the durable write | raw exit | test duration | log |
| --- | --- | --- | --- | --- |
| `cause-inject2-old` | 2 s | 0 | `passed (3.262 s)` | `cause-inject2-old.log.gz` |
| `cause-inject4-old` | 4 s | 0 | `passed (5.211 s)` | `cause-inject4-old.log.gz` |
| `cause-inject4-fixed` | 4 s | 0 | `passed (5.155 s)` | `cause-inject4-fixed.log.gz` |

The 4 s leg is the finding: the "≈3 s" budget tolerated a 4 s durable path, so
its expiry point is host-dependent — exactly why the issue asks for a
*deadline*, not a longer count.

**2. Only a lagging *publish* can stress these waits.** A delay inside the
awaited model call is absorbed before the wait starts (`await switchPhase(...)`
returns only after `enqueueDirectWrite` has refreshed the queue count; same for
`await refreshAll(...)`). The hosted log's shape is different: the durable write
has landed, the *published* count lags, and the wait polls into that gap. The
probe that reproduces that shape moves the publish out of `refreshQueueCount`
(`Sources/App/AppModel.swift:10672-10680`) into a deferred `Task`
(`probe-asyncpub30.diff`) — the item is on disk immediately, the model's
published count arrives 30 s later.

| leg | product (scratch copy) | test under measurement | raw exit | result | log |
| --- | --- | --- | --- | --- | --- |
| `cause-asyncpub30-old` | deferred publish, 30 s | **old** 600-poll budget + a print-only probe that reports the budget it burned | **65** | `failed (12.154 s)` | `cause-asyncpub30-old.log.gz` |
| `cause-asyncpub30-fixed` | deferred publish, 30 s | **hardened** (60 s deadline) | **0** | `passed (91.495 s)` | `cause-asyncpub30-fixed.log.gz` |

The old leg fails with exactly the hosted message, and its print-only probe
reports what the "≈3 s" budget was actually worth on this host:

```
PROBE-BOUND: the 600 x 5 ms budget burned 4.219004034996033 s before expiring
PROBE-BOUND: the 600 x 5 ms budget burned 3.7341339588165283 s before expiring
queue never reached 1; last observed 0
```

(~6.2-7 ms per iteration, not 5 ms — the budget is a spin count, so its
expiry point moves with the runner's scheduling; the hardened leg absorbs the
same 30 s deferral and passes, and prints no expiry diagnostics.)

That pair is the demonstration the brief asks for — same product shape, same
simulator, same fresh container, one variable (the wait):
the old budget expires, the hardened wait does not. It is an *artificial*
reproduction of the hosted symptom's shape (a lagging published count), not of
host contention: the contention I could actually apply locally is reported
above and did **not** expire the old budget.
