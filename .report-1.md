## Acceptance criteria

### AC1 — a settings change or phase transition records durable account-scoped intent BEFORE durable acceptance is presented → **PASS**

- `switchPhase` calls `enqueueDirectWrite(.phaseTransition(intent), …)` first: the intent
  (account scope, target block, intended date, the pre-state and the intended settings) is
  in the existing `DurableQueue` file before the optimistic periods/settings are published
  (locally or in memory). A `nil` return means nothing local changed, the failure is
  surfaced (`surfaceDirectWriteNotPersisted`), and the switch is never reported as saved —
  this also closes the #916 follow-up "queue-unavailable leg returns silently" **for this
  write path** (the preset/routine callers were not widened).
- Evidence: `testOfflinePhaseTransitionIsDurableAndReplaysOnceAfterProcessDeath` reads the
  raw `pending-writes.json` after an offline switch and asserts the account uuid, the
  selected block (`"strength"`), the intended date and the pre-state start date are on
  disk (`the test passed (1.270s) and its queue-file assertions cover the account uuid, the selected block, the intended date and the pre-state start date`).

### AC2 — termination before the request, between the related transition writes, and after server success before local acknowledgement are recoverable with no duplicate phase periods and no mismatched `currentPhase`/history → **PASS**

The transition is ONE intent; the replay order that makes the windows converge is
documented in `docs/evidence/issue-917/replay-order-and-windows.md`. The three windows are
driven individually through persisted state (a fresh `AppModel` over the same on-disk
queue + cache), with the stub applying the server-side writes the way a kill would leave
them:

| window | test (all in `PhaseTransitionReplayAppTests`) | observed |
|---|---|---|
| before the request | `testOfflinePhaseTransitionIsDurableAndReplaysOnceAfterProcessDeath` | 0 server writes while offline → one open `strength` period after the relaunch replay, 2 periods total, settings `.strength`/today, `pendingCacheWriteCount == 0` |
| between the related writes (close landed, create did not) | `testTerminationBetweenRelatedTransitionWritesDoesNotDuplicateThePeriod` | after the kill: 1 period, no open block, settings stale; after the replay: 2 periods, ONE open `strength` block today, settings matching |
| between the related writes (delete landed, reopen did not — same-day switch-back) | `testSameDaySwitchBackReopensThePreviousBlockWithoutASecondPeriod` | after the replay: 1 live period (the previous block, reopened with its ORIGINAL start date — no one-day sliver, no third period) |
| after server success, before local acknowledgement | `testTerminationAfterServerSuccessBeforeLocalAcknowledgementReplaysIdempotently` | the server was fully applied with the local rows still unacknowledged (3 pending); the replay re-sent nothing and the local rows settled (`pendingCacheWriteCount == 0`) |
| after the period half landed, before the settings half | `testLostSettingsHalfIsCompletedFromTheServerState` | the settings row is completed from the server state; no duplicate period |

### AC3 — retry uses a stable operation identity and preserves ordering; an old completion must not clear newer local settings → **PASS**

- Stable identity: the intent carries `operationID` + the immutable target/date, and it
  survives a fresh queue instance over the same file
  (`testPhaseTransitionIntentSurvivesAFreshQueueInstanceOverTheSameFile`, Core).
- Ordering: the transition is one item per account (the newest switch replaces the pending
  one), and the replay settles periods before the settings row.
- The newer-local-settings rule is exercised by
  `testOlderTransitionCompletionCannotClearANewerLocalBlock`: a first switch is held
  in flight, a second (same-day switch-back) writes newer local rows, the first
  completion then arrives while the second's own replay is refused by the server — the
  published block must stay the newer one, with its start date, and the queue must still
  hold the newer intent. Probe C (revision comparison removed) makes this test fail.

### AC4 — existing cache-only residues get explicit recovery/needs-attention handling, including pending deletes → **PASS**

`recoverLegacyPhaseResidues` runs once per account on the drain path (next to the #916
migration) and resolves only what is provable:

- a live pending row the server already serves with the same content → the server row is
  adopted and the optimistic identity retired;
- a pending tombstone whose identity the server no longer serves → the delete is already
  effective, confirmed;
- the settings row (a `user_id` singleton) → retired when the server serves exactly the
  pending value.

Everything else stays exactly where it is and keeps counting as unsynced: the sweep writes
nothing to the server, invents no transition, and never clears a period that disagrees
with the server (there is no per-mutation period writer to replay it with).
Evidence: `testLegacyPhaseResiduesAreRecoveredOnlyWhenProvable` (5 seeded residues → 2
resolved, 3 left, `queuedWriteCount == 0`, `server.periodCount == 1` unchanged).
