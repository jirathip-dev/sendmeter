## Which assertion lines remain unstable, and why

With the hardened waits in place, **no assertion line in this file failed in
11/11 quiet+contended runs**, so none is claimed unstable at this head. The
mechanism attribution (evidence in `root-cause-notes.md`, raw container dumps in
the ledger):

- `:88`/`:98` (the hosted failure set): **ordering/interleaving** between the
  model's own optimistic publication, the detached upload's acknowledgement
  (`AppModel.swift:7845` `Task { upload(item) }` → `publishIfCurrent`), and the
  cache hydration that replaces `recordings` and resets the pending overlay
  (`hydrateCachedWorkspace`, `AppModel.swift:2145/2160`) — plus **container
  state**: the test's fixed account id (`94000000-…-0940`) plus one shared
  on-disk app container across repetitions mixes runs' rows. That mixture is the
  "moving assertion lines" signature; on a clean container the base tree itself
  passes (base-2b).
- `:52` (seen failing historically): same shared-state path — `tindeqEntryCount`
  reads a published sessions array that a hydration can repopulate from an
  earlier run's container rows.
- `StructuralHapticsWiringTests:111` (seen failing at base on a reviewer's fresh
  sim): **unattributed — environment, not timing.** The assertion is a static
  scan of `Sources/**` for a literal present exactly once at base/head/reviewer
  head (verified by `git grep` at `0516b657`, `3bbec7e`, `c273627f0`); there is
  no wait to harden and it passed 11/11 here. Missing measurement: the reviewer's
  base-run container/filesystem state, which is not in this lane's possession.
