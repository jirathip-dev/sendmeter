## 5. The race-free `Gate` patch (written here, exercised in a scratch clone, not applied)

The lane's fence is docs-only; the fix lands in a **test file**, so the orchestrator routes
it. Diff: `docs/evidence/issue-956/gate-race-fix.diff` (one helper, ~9 changed lines, no
assertion touched). It makes "decide + register" atomic under an `NSLock` so `open()` can no
longer drain the waiter list between `wait()`'s `isOpen` check and its `waiters.append`:

```swift
func wait() async {
    await withCheckedContinuation { continuation in
        lock.lock()
        if isOpen {
            lock.unlock()
            continuation.resume()
        } else {
            waiters.append(continuation)
            lock.unlock()
        }
    }
}
```

**Measurement (scratch clone, `cp -Rc` of the lane tree, `.git` removed, module cache
cleared, `NSUnbufferedIO=YES`, focused filter, quiet host):**

| leg | runs | hangs | detail |
| --- | --- | --- | --- |
| RED — unpatched clone | 12 | **0** | run 1 rebuilt (62 s), runs 2–12 warm at 5–6 s each |
| GREEN — patched clone | 12 | **0** | all 5–6 s; patch applied with an assertion that the replaced block occurs exactly once |

**This does not discriminate, and the report says so:** the lane tree produced 6 hangs in
26 invocations in the same period, while this clone produced none in 12 (P ≈ 5 % if the clone
had the lane's rate, so it may be bad luck or a real clone/state difference — e.g. the
rebuilt `.build` or scheduling). The patch is therefore offered as a **reasoned** candidate
whose mechanism is established by (a) the source-level race, (b) the runtime's own
`SWIFT TASK CONTINUATION MISUSE: wait() leaked its continuation without resuming it.`, and
(c) the idle-waiter stacks — **not** as a measured cure. The decisive measurement is named in
§9.

## 8. The actual serving model (runtime mechanism)

`just core` → `swift test --package-path native/SendmeterNative` → the SwiftPM driver
(`swift-test`) builds into `native/SendmeterNative/.build` and runs the bundle as a separate
`xctest` process **in its own process group**. Inside that runner, every test is invoked
through XCTest's async bridge (`invokeWithAsynchronousWait` → `XCTWaiter`), which parks the
runner's main thread in a CFRunLoop wait until the test's Swift task completes.

- The **core-suite hang** is served by test-local state: `Gate.wait()` appends an unserialized
  `CheckedContinuation` while `open()` on the other executor may have already drained the
  list; the continuation is never resumed, the test's task never completes, XCTest's waiter
  never returns, the runner idles at 0 % CPU and the driver waits on its pipe. Nothing in the
  product is load-bearing: `GuidedForceTerminalSettlement.start()` is `@MainActor`-serialized
  and behaves as designed.
- The **misleading "stopped at test X"** is served by stdio block buffering of the piped
  runner stdout — the unflushed tail is invisible and the last visible line is a flush
  boundary, which usually lands in the previous class.
- Deliberately **not** load-bearing: SwiftPM's resolution/build lock (it announces itself
  loudly and never appears in a hang log), the `just` wrapper (it only reports the signal it
  saw), and the host's load (H3 fired at 1-min load 2.39; H6 stayed frozen after the load had
  subsided).
- The **app-target `queue never reached`** failure is served by *time in the harness's fixed
  poll budget* (600 × 5 ms ≈ 3 s) — and, on a container that already holds the row, by the
  already-applied pre-state skip. The **runner-launch failure** is served by the simulator
  test-runner attach path (measured here: the app launches, idles, no runner attaches). The
  **600 s diagnostics timeout** is served by `xcodebuild`'s post-failure simulator-diagnostics
  collection, not by the test run.
- The **"contention" around simulator gates** is substantially the tooling itself: erase+boot
  spawns up to 467 `CoreSimulator` processes and a ~235 1-min load on 10 CPUs, decaying over
  minutes.
