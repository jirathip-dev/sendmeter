## The shared-reader extension (reported, per the fence)

`Sources/Core/DeltaCursor.swift`, `b2b7134`'s diff against base
(`f9b2299…` → `bd49e60…`):

- `DeltaPageQuery.queryItems(select:tieBreakColumn:cursor:pageSize:timestampColumn:)`
  — the timestamp column is now a parameter of the `order`, the composite
  `or=(<ts>.gt.<stamp>,and(<ts>.eq.<stamp>,<tb>.gt.<id>))` filter and the
  legacy `<ts>=gte.<stamp>` filter. `updated_at` remains the default.
- `DeltaPageReader(timestampColumn:tieBreakID:)` — `timestampColumn` feeds the
  query and the checkpoint; `tieBreakID` is the value the reader writes into
  the composite checkpoint and validates page order against, defaulting to
  `entityID`. Only `user_settings` needs the split (constant cache id vs
  `user_id` tie-break).
- No cursor format change: `DeltaCursor.parse`/`persisted` are untouched, so a
  persisted S01 cursor is still read byte-identically (AC5).

The design decision: **one** paging implementation. The workout attempt
collection is not a fourth paging scheme — it is the same reader with
`timestampColumn: "started_at"`, `tieBreakColumn: "id"` and the parent
`workout_id` filter appended per page.

## AC3 — workout/attempt aggregation publication boundary — PASS

The publication boundary in code:

- `CachedWorkspace.reconcileServerDelta` is the only path that publishes a
  delta as a **finished authoritative snapshot**: it tombstones every cached
  row absent from the delta and then `markSyncComplete`s the entity
  (`Sources/Core/CachedWorkspace.swift`, unchanged). It runs on the
  first-sync/full-reconcile path of sessions, recordings, workouts and every
  remaining entity.
- The repository can only hand it a delta the reader produced **after** the
  last page: a capped response continues (`rows.count == pageSize ||
  rows.count < totalCount`), a failed page throws before any delta exists, and
  the page budget throws instead of truncating. `fetchWorkoutDelta`'s doc
  comment states this contract at the entrypoint (#915 AC3).
- `fetchWorkoutAttempts(id:)` — the workout's child attempt collection — is
  read by the same reader to completion; a capped/failed/over-budget read
  throws, so the detail's `.loaded(trace:attempts:)` state can never be a
  silent prefix of the workout's attempts, and each attempt keeps its real
  `climb_attempts.id` (previously a per-fetch random `UUID()`).

The tests that bite when it is violated:

- `PagedDeltaPublicationBoundaryTests.testGroupedWorkoutSnapshotIsPublishedOnlyFromACompleteRead`
  (5 workouts with attempt groups over 3 capped pages, then a cursor-bounded
  read of 6; asserts every row published, every attempt group intact, no
  absent-row tombstone, composite checkpoint, and the boundary only after the
  complete read).
- `PagedDeltaRemainingEntityTests.testWorkoutAttemptsCollectionIsReadCompletelyWithinItsWorkoutScope`
  (4 capped pages, parent-scoped — an attempt of another workout is never
  returned) and `…testWorkoutAttemptsMiddlePageFailureThrowsInsteadOfReturningAPartialCollection`
  (page 2 fails → throws, nothing published).
- RED splice B (below) shows the first test failing on exactly the violation.

- `…testAccountChangeAfterAPagedFetchAwaitRejectsTheStalePublication` — the
  paged fetch completes for account A (asserted: all pages served), the live

- The repository's paged path captures no live account value before its

  account-derived value on the fetch side and the publication gate reads the
  live pair, as the two tests above prove. No consumer file was modified
