## Design note (why the rest carries the hand-off)

The fullscreen call site receives a `ForceProtocolStage` and the preset — never the run — so the
upcoming stage's side (a run-level choice: a single-side selection, or the alternation pair's first
hand) is not derivable from `(preset, current stage)`. `ForceProtocolSchedule.stages(...)` is the only
place that knows the run's work sides and each set's hold ramp, so it stamps the hand-off onto the
rest stage (`ForceProtocolWorkHandoff`) — the same way `prepare`/`switchSide` already carry the side
they lead into. Consequently no stage list is regenerated and there is no index lookup to drift; the
`testRestHandoffMatchesTheRunStageItLeadsInto` matrix is the proof that the stamped hand-off *is* the
run's next work stage for every preset shape and side selection the app builds.
