## Acceptance criteria

### AC1 — persist account + operation/entity identity + immutable mutation before durable local acceptance → **PASS**

- `savePreset` / `saveRoutine` (create+update) and `deletePreset` /
  `deleteRoutine` now call `enqueueDirectWrite(...)` **first**: the intent is
  written to the existing `DurableQueue` file before the optimistic cache row,
  the published list and the `true` return value exist. `nil` (queue
  unavailable, persistence error, account change, terminalised identity) means
  nothing was written locally, the failure is surfaced, and the caller gets
  `false` — never a saved state.
- Evidence: `testOfflinePresetSaveReplaysAfterProcessDeathExactlyOnce` /
  `...Routine...` read the raw queue file and assert the account uuid, the
  entity uuid and the mutation content are on disk before the drain:
  `the intent is persisted for this account`, `the entity identity is
  persisted`, `the immutable intended mutation is persisted` (log
  `green-app-restored.log`), plus the Core round-trip test
  `testDirectWriteIntentSurvivesAFreshQueueInstanceOverTheSameFile` (13 Core
  tests, 0 failures, `green-core-policy-restored.log`).
- One item per entity (`id` = entity id, `terminalKey` = entity id) → a
  create→update→delete sequence never leaves two racing intents.

### AC2 — offline save → termination → relaunch → reconnect completes it; create→update→delete cannot resurrect → **PASS**

- `testOfflinePresetSaveReplaysAfterProcessDeathExactlyOnce`: offline save
  accepted (`presetInsertCount == 0`), a **second `AppModel` over the same
  on-disk cache + queue** (process death simulation) restores the pending row
  from the cache and the intent from the queue file, then the replay performs
  `presetInsertCount == 1` with the intended content, `pendingCacheWriteCount
  == 0`, list length 1. Same for routines
  (`testOfflineRoutineSaveReplaysAfterProcessDeathExactlyOnce`).
- `testPresetCreateUpdateDeleteCannotResurrectTheRemovedEntity`: offline
  create → update → delete leaves exactly ONE intent (the delete), the drain
  performs 0 inserts and 0 rows remain; a later create for the same identity
  is refused (`zombieAccepted == false`) because the completed delete
  terminalised that identity in the queue.

### AC3 — lost acknowledgement retries idempotently; an older ack cannot clear a newer pending revision → **PASS**

- `testLostPresetInsertAcknowledgementRetriesIdempotently` /
  `testLostRoutineInsertAcknowledgementRetriesIdempotently`: the stub applies
  the insert and then **drops the response** (`presetInsertCount == 1`, item
  still queued); the retry finds the identical active row through
  `fetchPresets()`/`fetchRoutinePresets()` and adopts it: `presetInsertCount`
  stays **1**, `activePresets.count == 1`, one local row, `pendingCacheWriteCount == 0`.
  (Both tables mint their own `id` and the insert payload carries none, so a
  blind retry would insert a second row — that is what the adoption prevents.)
- `testOlderPresetAcknowledgementCannotClearANewerPendingRevision`: the first
  edit's PATCH is held while a newer edit lands (revision 2). When the stale
  response arrives, `confirmDirectWriteSaved` compares the captured revision
  with the current one, does **not** publish the older row over the newer one
  and does **not** clear it (`pendingCacheWriteCount == 1` while the newer edit
  is pending; the published row stays `Edited B`). After the replacement
  uploads, the server row is `Edited B` and the pending flag clears.

### AC4 — existing pending cache-only rows: migrated with provable intent or exposed as needs-attention → **PASS**

- The drain path adopts pending cache-only rows through
  `migrateLegacyDirectWrites` / `adoptLegacyDirectWrites`: the row is the
  evidence (`DirectWriteReplayPolicy.legacyOperation`: tombstone → delete;
  server still has the id → update; otherwise → create, and the create is
  content-checked before it is sent). Undecodable payloads are **left alone**
  (`continue`) and keep counting in `pendingDirectWriteCount` (the existing
  "N unsynced" surface) — never cleared, never guessed.
- Evidence: `testLegacyPendingPresetCacheRowIsAdoptedWithProvableIntent` seeds
  a pending cache row with **no** queue item (`pendingCacheWriteCount == 1`,
  `queuedWriteCount == 0`), then the drain performs exactly one insert and
  reconciles the row (`pendingCacheWriteCount == 0`).
- The pre-existing phantom is fixed too: a create whose insert mints a
  server-side id now retires the local optimistic identity
  (`confirmDirectWriteSaved` → `upsertServer` + `confirmServerDelete`) instead
  of leaving a permanently-pending row; the relaunch tests assert
  `pendingCacheWriteCount == 0` afterwards (and the RED run shows `1` without
  the fix).

### AC5 — disk failure surfaced; account switch cannot drain under another user; permanent rejection stays recoverable → **PARTIAL**

- Account scoping: every new path takes a captured `AccountScopedFetch` and
  re-checks `canApply(to:accountEpoch:)` after each await; the queue APIs
  require the owning `accountUserID`; the legacy adoption and the drain are
  both per-account. Evidence:
  `testQueuedPresetIntentForOneAccountIsInvisibleToAnother` — account B's
  `retryAllQueuedWrites` performs **0** inserts while account A's intent is
  queued, B's counters are 0 and its list is empty; A then replays it once.
  **Not provided**: a full sign-out / sign-in switch test (the user-initiated
  sign-out path has its own drain + remainder prompt; the account-scope
  invariant is proven at the queue level above, not through the sign-out UI
  flow).
- Disk failure: `enqueueDirectWrite` returns `nil` on a persistence error /
  unavailable queue, the caller writes nothing locally and reports failure via
  `surfaceDirectWriteNotPersisted()` ("This change couldn't be saved on this
  device.") — no saved/synced status. **Not verified by a test**: there is no
  injectable filesystem seam for the queue directory in `AppModel` (it derives
  the app-container path itself), so the failure branch is code-path evidence
  only.
- Permanent rejection: replay failures go through the unchanged
  `markFailure`/quarantine path; `DirectWriteReplayError.missingIntendedMutation`
  (a corrupt envelope) conforms to `ServerRejectionClassifying` as
  `.permanent`, so it spends the bounded attempts and lands in the existing
  quarantine, where the existing retry/discard UI can recover it.
  `writeKind` reports "Preset" / "Routine" so the Settings surface names it.
  Evidence: Core test `testMissingIntendedMutationIsAPermanentRejection`.
